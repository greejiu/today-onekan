## 검증 환경과 범위

운영 사용자 데이터를 테스트에 사용하지 않았다. 로컬 PGlite 0.5.8에서 실제 SQL을 실행하고 가상의 세 사용자·Auth/Storage 스키마로 권한을 검증했다. Playwright + Chrome으로 실제 앱을 열되 네트워크를 전부 가로채고 이 로컬 DB와 연결했다. Supabase Auth/HTTP/Storage 전송 계층은 모의 구현이다.

`tests/together-sql.cjs` — 58개 검증 통과:

- 비로그인 RPC 거부, 로그인 후 2인 참여, 제3자 정원/조회 차단, 초대 만료·취소·이미 참여함·방장 권한.
- 계획별 양의 정수, 원본 소유권과 제목만 복사, 습관 날짜별 중복 연결 방지.
- 내 인증 승인 거부, 여러 번 승인 요청에도 적립 1회, 승인자/시간 보존, 점수·증빙 직접 수정/삭제 불가.
- 초과 사용 거부, 재시도 사용 1회, 취소 복원 1회, 총 적립 보존. 동시에 보낸 요청 중 잔액에 맞는 요청만 성공.
- 초안 및 초안 사진의 상대 접근 차단, 공개 후 접근 허용, 본인 일기/답글 수정·삭제만 허용, 제3자 모든 신규 데이터 접근 차단.

## 미검증과 원격 적용

- **운영 DB 마이그레이션, 코드 배포, 커밋/푸시는 하지 않았다.** 이 변경을 실제로 사용하려면 SQL 적용과 프런트 배포가 필요하다.
- 원격에는 읽기 전용으로 `information_schema.columns`와 Storage 정책만 조회했다. `tok_habits.name`, `tok_todos.title`, UUID 소유자 키를 확인했다. 기존 Storage 정책은 `onekan-user-assets` 버킷에 한정되어 새 버킷과 겹치지 않는다.
- 실제 Supabase 로그인 2계정·Storage 업로드 API·서명 토큰·재로그인은 미검증이다. 로컬 브라우저의 계정은 테스트 세션이다.
- PGlite는 연결 요청을 직렬 실행하므로 실제 PostgreSQL 다중 연결의 잠금 대기·교착·동시 초대 경쟁은 검증하지 못했다. 코드에는 같은 방 행 잠금과 unique 제약이 있다. 운영 적용 전 별도 테스트 DB의 다중 연결로 확인해야 한다.
- 운영 보안 Advisor는 새 스키마가 아직 적용되지 않아 이 변경을 대상으로 실행할 수 없었다. 적용 후 새 테이블/함수/버킷 관련 항목을 확인한다.
- 물리적 휴대폰·Safari는 미검증. 실패 후 같은 열린 입력창에서 재시도는 지원하지만 저장하지 않은 입력의 새로고침 복원은 제공하지 않는다. 고아 이미지 서버 정리는 후속이다.

## 적용 후 최소 수동 확인

1. A로 **모바일 더보기 → 같이 한칸 → 방 만들기**. 환산율·별명을 확인해 저장하고 코드를 B에게 전달한다.
2. B는 별도 브라우저에서 로그인하고 초대 수락. C의 같은 코드 참여 및 데이터/이미지 조회가 차단되는지 확인한다.
3. A가 5점 계획과 사진 인증을 등록한다. A의 자기 승인 시도가 실패하고 B의 확인 재시도가 한 번만 적립되는지 확인한다.
4. A가 3점 보상을 기록하고 취소를 두 번 요청한다. 잔여가 5점이며 총 적립 5점이 보존되는지 확인한다. 서로 다른 두 요청으로 잔액 초과 동시 사용도 확인한다.
5. A가 사진 포함 초안을 저장한다. B에게 글/사진이 숨겨지고 ‘함께 보기로 올리기’ 이후 조회·답글이 가능해야 한다. 새로고침 및 재로그인 후 유지되는지 확인한다.

정책: 계획 점수는 직접 입력하는 **임시 구현 기준**, 100원/점은 방 생성 시 변경 가능한 **제안 기본값**이다. 4인 승인 인원·중도 참여 과거 글·멤버 교체·환산율 변경·인증 정정·보상 공개 범위는 아직 결정하지 않았다.
