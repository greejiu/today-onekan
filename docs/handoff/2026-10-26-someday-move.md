## 목표
언젠가(담아두기) 줄을 날짜·시간에 놓으면 일정·할일·습관 중 하나로 만들어 옮긴다.
조건은 다음과 같다.
- 저장에 성공했을 때만 옮겨진다.
- 취소하거나 실패하면 원본이 그대로 남는다.
- 응답을 못 받고 다시 시도해도 두 번 생기지 않는다.

## 한 일
- **마이그레이션** `supabase/migrations/20261026000000_tok_someday_move_any_kind.sql`
  - `tok_someday_moves`: 옮긴 기록 표(언젠가 항목 하나당 한 줄).
    - 로그인 사용자는 **본인 것 읽기만** 할 수 있다. 넣기·고치기·지우기 권한이 없고, 쓰기 정책도 없다.
    - Supabase가 새 표에 기본으로 주는 권한도 거둔다(`revoke all … from public, anon, authenticated` 뒤 `grant select`).
    - 기록은 이동 함수가 실제로 옮겼을 때만 생긴다. 직접 만든 가짜 기록으로 "이미 옮겨짐"이라고 속이는 길을 막았다(2026-11-02 결 검토).
  - `tok_move_someday(p_someday_id, p_request_id, p_kind, p_row)`: 한 거래 안에서 다음 세 가지를 함께 한다.
    1. 언젠가 행 삭제
    2. 고른 표에 새 행 추가
    3. 옮긴 기록 남기기
  - 기록이 이미 있으면(재시도, 다른 창) 새로 만들지 않는다. 대신 처음 결과(`replayed`, `same_request`, `item_exists`)를 돌려준다.
  - 종류마다 허용한 칸만 받는다. id·user_id·완료·반복 연결 칸은 받지 않는다.
  - **security definer**(기록 표에 쓰려고). 행 보안(RLS)을 건너뛰므로 "본인 것만"을 함수 안에서 직접 지킨다.
    - 언젠가는 `user_id = auth.uid()`인 행만 지운다.
    - 새 항목은 `user_id = auth.uid()`로 넣는다(`p_row`로는 user_id를 받지 않는다).
    - 다시 돌려주는 결과도 본인 것만 본다.
  - 범주·그룹·프로젝트 주인은 기존 `(id, user_id)` 외래키가 검사한다. 기간·그룹 종류·목표 연결은 기존 트리거가 검사한다. 이 트리거들은 각자 `search_path=public`이고 새 행의 user_id로 확인한다.
  - `search_path = ''`이고 모든 이름을 스키마까지 적었다.
  - 이 마이그레이션은 운영 DB에 아직 적용한 적이 없어서, 새 파일을 더하지 않고 같은 파일을 고쳤다.
- **앱** `index.html`
  - 언젠가를 끌어 놓은 뒤의 흐름은 다음과 같다.
    1. 종류 메뉴가 뜬다(`openSomedayMoveFromDrop`).
    2. 고른 종류의 추가창이 열린다(`openSomedayMoveWindow`).
    3. 저장하면 함수를 한 번 부른다(`saveSomedayMoveRow`).
    4. 결과를 안내한다(`finishSomedayMove`).
  - 창이 열릴 때 요청 키 하나를 만든다. 다시 저장할 때도 같은 키를 쓴다.
  - 결과를 모르면 옮긴 기록과 원본을 읽어 다음 중 무엇인지 판단한다: 옮김 / 그대로 / 이미 없음 / 확인 못함.
  - 놓은 자리별로 채우는 값
    - 날짜 칸·하루종일: 그날 하루종일
    - 타임라인: 그 시각부터 30분
    - 시간블록: 블록 시작부터 30분
  - 가져오는 것: 제목, 범주, 프로젝트(할일·습관만). 그룹은 도착 공간의 기본으로 시작한다. 못 가져오는 것은 창 위에 안내한다.
  - 옛 끌기 저장(할일 만들기 → 언젠가 지우기, 요청 2번)은 지웠다.
  - 끈 직후 놓은 달력 칸의 클릭이 종류 메뉴를 덮지 않도록 그 클릭 한 번은 무시한다.

- 통과

  - `someday-move-concurrency` 6묶음(실제 PostgreSQL 16 테스트 서버, 운영 DB 아님, 4번 연속 통과)
    1. 같은 요청 키로 두 연결 동시: 둘째가 첫 연결의 잠금을 기다린 뒤 처음 결과를 받는다 → 항목 1·기록 1
    2. 다른 요청 키로 두 연결 동시: 둘째는 만들지 않는다 → 항목 1·기록 1
    3. 먼저 쪽 실패(되돌림, 함수 안 오류): 둘째가 옮긴다. 첫 쪽 항목은 남지 않는다
       - 함수 안에서 오류가 나면 Postgres가 그 거래를 바로 끝내고 잠금을 풀어서, 둘째는 기다리지 않는다
    4. 늦은 쪽 잘못된 값: 먼저 쪽이 성공하면 결과만 받는다. 양쪽 다 실패하면 원본 그대로·항목 0·기록 0
    5. 연결 8개 동시(같은 키·다른 키): 실제로 옮긴 요청은 1개, 모두 같은 항목
    6. 실제 서버에서도 기록 표 직접 넣기·고치기·지우기 거부
