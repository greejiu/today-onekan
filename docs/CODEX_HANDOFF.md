## 4. 확정된 제품 방향

### 집 3열

- 웹 순서: **언젠가 | 지금, 한칸 | 다가오는**.
- 너비 기준안: 30% / 40% / 30%. 가운데를 가장 넓게 둔다.
- 두 개로 묶였던 담아두기 탭을 독립 카드 두 개로 분리한다.
- 가운데는 기존 시간블럭/타임라인을 선택해서 본다. 두 보기는 같은 날짜를 공유한다.
- 화면 가용 높이에 카드 세 개를 맞추고 목록 각각 내부 스크롤. 글자를 줄여 모든 항목을 억지로 한 화면에 넣지 않는다.
- 오른쪽 주간 탐색은 가운데 선택 날짜와 분리한다.
- 마지막 가운데 보기와 보기별 스크롤 위치를 기억한다.
- 모바일 새 영역 전환 탭은 아직 상세 확정 전. 1단계는 좁은 화면에서 3열을 강제하지 않고 현행 세로 스크롤 동작을 보존하는 대체 배치.
- 사용자의 원본 스크린샷은 약 30% 축소 화면이었다. 그 빈 공간을 100% 실제 배치로 판단하지 않는다.

### 타이머 — 후속 구현

- 독립 타이머 메뉴 + 다른 화면에서도 보이는 작은 진행 표시.
- 대상: **할 일만**. 일정·습관·언젠가에는 직접 타이머 시작을 제공하지 않는다.
- 시간 재기(스톱워치) / 시간 정하기(카운트다운) 기본안.
- **종료하면 시간 기록만 저장. 할 일 완료는 사용자가 체크.**
- 완료 여부 질문, '할 일도 완료', '저장하고 할 일 완료' 버튼을 만들지 않는다.
- 화면 이동·새로고침 복원, 실제 경과시간 측정, 일시정지 시간 제외, 동시 실행/저장 중복 방지, 할 일 삭제 후 기록 보존을 고려한다.
- 목표 시간 도달·첫 실행 기본값·여러 기기·앱 종료 정산은 설계 중이다.
- 대화에서 보여준 미리보기는 예시 데이터의 동작 설명이며 실제 저장·동기화가 구현된 앱이 아니다.

### 공통 메뉴 — 후속 구현

| 항목 | 순서 |
|---|---|
| 할 일 | 오늘 하기 → 내일 하기 → **타이머 시작** → 수정 → 그룹 변경 → 복제 → 삭제 |
| 언젠가 | 오늘 하기 → 내일 하기 → 수정 → 그룹 변경 → 복제 → 삭제 |
| 일정 | 오늘 하기 → 내일 하기 → 수정 → 범주 변경 → 복제 → 삭제 |
| 습관 | 이번만 건너뛰기 → 수정 → 그룹 변경 → 복제 → 삭제 |

- 오른쪽 클릭과 ⋯는 동일한 메뉴.
- 오늘/내일은 실제 오늘 기준. 완료 처리가 아닌 날짜 이동.
- 기존 시각·소요시간·여러 날 일정의 기간을 보존한다.
- 별도 날짜 수정 메뉴는 없애고 수정창에서 임의 날짜를 지정한다. 언젠가 수정창에도 해당 이동 진입점이 필요하다.
- 습관은 건너뛴 상태에서 건너뛰기 취소를 제공하며 완료한 회차에는 건너뛰기를 숨긴다.
- ×는 상태 표시이며 클릭해서 완료할 수 없다.
- 삭제 라벨 확정이 과거 기록까지 삭제하라는 뜻은 아니다. 기존 습관 기록 보존 원칙 유지.
- 할 일의 타이머 시작은 내일 하기 바로 아래. 언젠가는 할 일로 옮긴 뒤 사용.

### 기록·통계 — 계속 설계할 부분

- 오늘 집중 기록을 기본으로 보고 그룹별·할 일별·프로젝트별 집계를 제공하는 방향.
- 프로젝트·포커스는 할 일만. 프로젝트의 그룹을 소속 할 일이 따른다는 기존 규칙 유지.
- 일/주/월, 수동 수정, 자정 넘김, 분류 변경 후 과거 통계, 프로젝트 연결 UI 등의 상세 결정은 아직 하지 않았다.
- 최신 설계 문서 5장에 미결정 목록이 있다.

라인 번호는 바뀔 수 있으므로 함수/ID로 검색한다.

| 탐색어 | 용도/주의 |

정적 검토에서 확인한 기존 위험:
1. 언젠가↔할 일 드래그와 메뉴 이동의 원자성·완료 상태 정책이 다름.
2. 여러 날 일정을 드래그하면 종료일을 null로 만드는 코드가 있음.
3. 습관 드래그가 해당 회차 이동처럼 보일 수 있지만 공통 시간 설정을 변경함.
4. 옛 주석·README와 현재 동작이 일치하지 않는 부분이 있음.

위 위험을 레이아웃 변경으로 해결했다고 보고하지 않는다. 데이터 이동 안전성 후속 작업으로 추적하고 타이머 데이터 연결 전에 정리한다.

## 6. Codex의 첫 작업 요청

**최신 저장소 기준으로 집 화면 3열 개편을 구현한다.**

1. 최신 main, 작업 트리, 진행 중 변경, 저장소 지침을 확인하고 기존 작업을 보존한다.
2. 전용 브랜치에서 작업한다. 기존 기술 스택을 교체하거나 전체 index.html을 새로 쓰지 않는다.
3. 최신 설계 문서 1·2·6·7장의 범위대로 3열 배치, 가용 높이, 내부 스크롤, 가운데 보기 기억, 오른쪽 독립 날짜 탐색을 구현한다.
4. 기존 DOM ID와 이벤트·드래그 연결을 점검하고 필요한 최소 구조 변경을 적용한다.
5. 3열 내 드래그 대상과 내부 가장자리 스크롤을 확인한다.
6. 하루종일, 빈칸 추가, 남아 있는 할 일, 그룹 필터, 언젠가 더 보기, 모바일 동작을 유지한다.
7. 타이머/신규 메뉴/프로젝트/통계/광범위한 DB·반복 모델 변경은 이번 패치에 넣지 않는다.
8. 1440×900, 1366×768, 390px 모바일, 확대/좁은 화면, 긴 제목/다수 항목/빈 상태를 검증한다.
9. 운영 계정 데이터를 테스트 목적으로 옮기거나 삭제하지 않는다. 테스트가 제한되면 실제 검증 범위를 명시한다.
10. 변경 내용, 검증 결과, 기존 결함과 새 회귀 여부, 남은 작업을 보고한다.
11. 전용 브랜치 커밋·푸시와 검토 가능한 PR을 준비한다. 이 인계 범위에는 main 자동 병합·운영 배포를 포함하지 않는다. 사용자의 추가 지시가 있으면 그 지시를 따른다.
